# 同步机制

## 操作日志方案（方案 B）

服务端维护两条独立的操作日志（变更链），每执行一次操作加一个版本号。

### 两条链

```
世界层日志（Version_W）        玩家层日志（Version_P）
同步给所有在线玩家             每人一条，只同步给对应玩家
├── Flag 变更                   ├── 节点破解状态
├── 防火墙破解                   ├── 发现用户
├── Faction Action 触发          ├── 个人节点文件变动
├── 节点可见性                   ├── 属性标记
├── 网络拓扑变动                 └── DLC 激活状态
└── 共享文件系统变更
```

### 入网同步

```
客户端连上来：
  -> 发 HELLO（携带 ownPlayerName, lastVersion_W, lastVersion_P）
  -> 服务端查 playerName -> playerId 映射表
     - 匹配 -> 恢复旧 ID
     - 不匹配 -> 分配新 ID 并持久化
  -> 服务端比对版本：
     - 世界层：从 lastVersion_W+1 开始发差异
     - 玩家层：从 lastVersion_P+1 开始发差异
     - 落后太多（超过阈值）-> 发全量同步
```

### 运行时同步

```
客户端操作 -> AC 事件检测 -> ServerPlugin 转发给控制台
  -> 服务端验证（节点存在？端口有效？冲突？）
  -> 分类：世界层还是玩家层
  -> 写对应日志，version++
  -> 世界层变更 -> 广播给所有人
  -> 玩家层变更 -> 只发给对应玩家
```

### 全量同步范围

全量同步时：
- 世界层：全部序列化发送（节点定义 + Flag + Faction 定义 + 共享文件系统）
- 玩家层：**只发目标玩家自己的那份**，不附带其他人的玩家层数据
- 临时层：不发

### 冲突处理

先到先得（First-write-wins）。
A 和 B 同时破解端口 2 -> 先到服务端的被执行，后到的版本不匹配被拒绝。
被拒绝的客户端收到最新版本后本地同步更新。

### 重连

```
客户端："我最后的世界版本=OP_W3，我的玩家版本=OP_P1"
服务端比对：
  世界层：从 OP_W4 开始发给客户端
  玩家层：从 OP_P2 开始发给客户端
两个互不干扰
```

### 修改权限

两层都是服务端权威。客户端不可信。
- 世界层：服务端验证节点状态后修改
- 玩家层：也需要服务端验证（防止客户端伪造破解状态）
- 区别只在于广播范围：世界层全发，玩家层只发给对应玩家

### 未覆盖的讨论点

| 点 | 说明 |
|----|------|
| 操作日志分层存储 | 世界层和玩家层存不同位置，但玩家层可能需要看到其他人玩家层的操作 |
| 层间操作同步顺序 | 如果一条世界操作依赖某玩家操作的完成，按什么顺序同步？目前想法：按 Delay 顺序发 |
| 全量同步范围 | Alice 掉线后重连，全量同步时是不是只发世界层 + Alice 玩家层？目前想法：是 |
| 操作日志压缩 | 版本号太多时需要压缩成快照 |
